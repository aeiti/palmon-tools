# Palmon Queue Planner — Formal Plan

**Project:** Build/research scheduling optimizer for Palmon: Survival
**Owner:** Adam (αειτι, R5 VOID, Server 111)
**Repo home:** `palmon-tools` (GitHub Pages + GitHub Actions)
**Status:** Mechanics model complete. Awaiting FotP stage-rate data (non-blocking; placeholders in use).

---

## 1. Objective

Maximize **personal points** across the two scoring systems — Guild Duel and Front of the Pack — at minimum resource cost, by recommending *when* to start queue items, *when* to burn speedups, and *when* to fire cooldown abilities.

Priorities, in order:
1. Hit personal reward thresholds (Duel point chests: 700k / 1M / 2.2M; FotP per-stage chest tiers).
2. Defend FotP cross-server leaderboard rank.
3. Guild outcome: ignored except as tiebreaker (matchmaking frequently unwinnable; e.g., VOID 0:9 vs HARK).

Threshold-seeking, not blind maximizing: once a day's realistic targets are hit, the planner recommends *stopping*, preserving inventory for better windows.

## 2. Verified Mechanics Model

### 2.1 Game clock
- All game scheduling runs on **UTC-2**. Use IANA zone `Atlantic/South_Georgia` (fixed UTC-2, no DST) for all internal math. Display in visitor-local time via `Intl`.

### 2.2 Guild Duel (weekly)
- 6-day week, **Sunday off**. Week boundary: Sun 23:00 → Sat 24:00 server time.
- Fixed weekday themes:

| Day | Theme | Queue-relevant scoring |
|---|---|---|
| Mon | Complete Intel Quests | — |
| Tue | Build Up Your Camp | Building speedups **125/min**; building power **10/pt** |
| Wed | Research Techs | Tech speedups **125/min**; tech power **10/pt** |
| Thu | Upgrade Palmon | — |
| Fri | Prepare for Battle | **All** speedup types 125/min; building **and** tech power 10/pt; training 125/min |
| Sat | Defeat Enemies | All speedup types 125/min (no power points) |

- **Friday = universal dump day.** Saturday = speedups only; completions should land Tue–Fri.
- Personal points accrue daily; rank rewards issued daily; chest tiers at 700k / 1M / 2.2M.

### 2.3 Front of the Pack (FotP, per-event)
- 5 stages × 4h slots, 6 slots/day: **Upgrade Palmon → Upgrade Buildings → Train Armigo → Research Techs → Spend AP** (cyclic), each day starting one stage later than the previous → 5-day super-cycle.
- **Re-anchors per event.** The opening stage is NOT stable across events (June event Day 1 opened Upgrade Palmon; August event Day 1 opened Spend AP). Each event requires a one-screenshot re-anchor: event start date + Day-1 00:00 stage.
- Current event anchor: Day 1 = Fri Aug 7, 00:00 UTC-2 (= Thu Aug 6, 7:00 PM PDT). Game days run 4 PM–4 PM Pacific.
- Per-stage: own action list with per-action stage points, own chest thresholds (varies by stage: Spend AP 6k/12k/30k; Upgrade Palmon 3k/7.5k/15k), event-level milestone track, cross-server leaderboard on cumulative event points.
- **Verified rates:** Spend AP (+100/AP, +1/Mount Feed, +300/Magic Bean); Upgrade Palmon (+1 per 2,000 Palmon XP, +500/hatch, +300/Magic Bean); Upgrade Buildings (+10 per min building speedup, +4 per 10 building power, +300/Magic Bean; chests 6k/12k/30k).
- **Unknown:** rates for Train Armigo, Research Techs; event duration; gap cadence between events.

### 2.4 Queues
- **4 building queues (B1–B4), 2 research queues (R1–R2), 4 training queues (T1–T4).** Ten named slots total.
- Queue items entered manually with remaining duration (read from game UI). No cost/duration database — ever. Power-gain values are not visible pre-completion → completions scored qualitatively ("lands power points, amount unknown"), not numerically.
- Training specifics: training speedups score 125/min on **Fri and Sat only** (no Tue/Wed-style theme day of their own, and no power-point completion stream in the Duel data). Train Armigo is a FotP stage, and Duel Day-5/Sat lists show per-Armigo-trained points scaling by level (75→338 for Lvl 1→10), so training *completions* carry Duel value on the right days in addition to speedup burns. **No cooldown entity touches training** — Instabuild is buildings-only, class skills cover build/research — so training queues are pure speedup-and-scheduling territory, and training depth going into Fri/Sat is the sole lever for training-speedup burns.
- **Healing (plannable, single hospital queue, capacity 18,000):** the hospital is one big queue, not parallel slots; injuries accumulate up to a hard cap of **18,000**, and **overflow becomes permanent deaths/losses**. Healing speedups score 125/min on Fri/Sat. Depth is generated by combat injuries rather than by starting jobs — and Duel Saturday *awards points for losses* (12→48 by Armigo level), so Saturday combat is self-feeding: fight → kill/loss points → injuries fill the hospital → healing burns score the same day. The overflow-deaths rule makes headroom management protective, not just optimizing: banked injuries occupy capacity that live combat will consume, and fighting near cap converts casualties into permanent losses. Planner treatment: hospital fill level is a runtime input; recommend holding midweek injuries as Fri/Sat burn fodder **only while projected headroom covers planned combat**; "hospital nearing 18k — heal down before fighting" is a first-class warning; no cooldown entity, pure speedup territory.

### 2.5 Cooldown entities (all manual-fire)

| Entity | Source | Effect | Cooldown | Points? |
|---|---|---|---|---|
| **Instabuild** | Camp order | −8h on all active **build** queues | 48h | **Yes** — counts toward Duel + FotP like speedup minutes, per queue touched (working assumption: 8h × 4 queues = up to 32 counted hours ≈ **240k Duel pts** at full depth on a scoring day; verify counter jump on next scoring-day pop) |
| **Instant Build** | Class skill | −600 min on all active **build** queues | 47.5h | No |
| **Instant Research** | Class skill | −600 min on all active **research** queues | 47.5h | No |

- Names deliberately similar; UI must label by source: "Instabuild (camp order)" vs "Instant Build (class skill)."
- No other camp orders in scope.
- **Manual fire ⇒ cooldowns anchor to actual fire time.** The planner recomputes from confirmed timestamps, never from theoretical cadence.
- Instabuild (48h): zero drift — phase-lock problem. Target phase: **Tue → Thu → Sat** (2 of 3 pops on building-scoring days; Thursday pop is dead point-wise but worth the time, or holdable).
- Class skills (47.5h): drift 30 min earlier per greedy cycle; ~3 pops/week. Intentional holds re-phase the cycle.

### 2.6 Speedups
- Types: building, tech, training, healing, **general**. Denominations: 1m, 5m, 1h, 3h, 8h.
- **General speedups count as the type they're spent on** for Duel scoring → generals are the flexible reserve: spent last, steered to whichever scoring day type-specific stock can't cover (Friday is the natural sink).
- Finite inventory; ballpark holdings per type entered at runtime; planner treats as budget.
- Denomination-aware recommendations: prefer consuming small units on scoring days (every fragment counts at 125/min); 8h blocks for moving big timers or deep burns fully absorbed by remaining time.

### 2.7 The queue-depth constraint (core coupling)
Speedup minutes only count when consumed against **active remaining timer time**. Scoring-day burns are capped by total remaining minutes across queues that day. Therefore:
- "Start this long build Thursday so Saturday has depth to burn into" is a *scoring* recommendation.
- Class-skill pops shave real time for free but **destroy burnable minutes** — 600 shaved min on a scoring day = 75k Duel points forgone vs. covering with real speedups. Rule: pop class skills on **dead days (Sun/Mon)** or on queues that will never be sped, and only up to the point where scoring-day queues stay deep enough for planned burns.
- Class-skill secondary use: **completion repositioning** — a pop pulls all completions ~10h earlier, which can move a power-bearing completion from a non-scoring day onto Tue/Wed/Fri.

### 2.8 Canonical week skeleton
- **Sun/Mon (dead):** pop class skills (free shaving); load queues.
- **Tue:** Instabuild pop #1 + building speedup burn (double-dip if an Upgrade Buildings FotP slot intersects).
- **Wed:** tech speedup burn; cover gaps with generals if warranted.
- **Thu:** optional dead Instabuild pop (or hold); start long builds **and load all four training queues** for weekend depth (training only scores Fri/Sat, so Thursday loading is its entire setup window).
- **Fri:** universal dump — everything scores; generals sink here.
- **Sat:** Instabuild pop #2 + remaining speedup burn (no power points; completions should already have landed).
- **Sat night → Sun:** Duel week ends 7 PM PT; class-skill anchor pop keeps their drifting cycle in cheap territory.

## 3. Scoring & Recommendation Engine

### 3.1 Inputs (runtime)
- Queue contents: item name, queue slot (B1–B4 / R1–R2 / T1–T4), remaining duration.
- Speedup inventory ballpark per type (+ denominations optional).
- Last-fired timestamps for the 3 cooldown entities.
- FotP event anchor (start date + Day-1 stage) and per-stage rates.
- User weighting knob: Duel-priority ↔ FotP-priority (leaderboard defense can justify "wrong day" FotP burns — e.g., #1 seat with a 4k lead).

### 3.2 Config (`scoring.json` inside `schedule.json` family)
Every rate carries `source: "verified" | "estimated"`. Recommendations driven by estimated rates are visually flagged. Placeholder strategy for the 3 unknown FotP stages: mirror Duel rate *shapes* (per-min speedup + per-power-point for Buildings/Techs; per-level curve for Train Armigo, shape from Duel Day-5 list: 75→338), magnitudes scaled to the two verified stages. First screenshot of each stage overwrites its block and clears the flag.

### 3.3 Core computations
1. **Rotation projection:** from the FotP anchor, enumerate all upcoming stage windows; intersect with Duel weekday themes → ranked **double-dip windows** (FotP stage ∩ Duel theme, e.g., Upgrade Buildings slot on a Tue/Fri/Sat).
2. **Back-scheduler:** for each queue item, candidate start times such that completion lands in a matching FotP window and/or power-scoring Duel day; rank by combined score.
3. **Burn planner:** per scoring day, recommended burn amount per type, capped by projected queue depth, drawn from inventory in achievable denomination combos, generals allocated last.
4. **Cooldown scheduler:** next-fire recommendations for the 3 entities under phase-lock (Instabuild → Tue/Thu/Sat) and drift-management (class skills → dead-day anchor), including explicit **hold** recommendations ("ready now; hold until Tue 9 AM").
5. **Warnings:**
   - Queue depth will fall below planned burn / below class-skill deduction at [time] (pop-now-or-lose-value).
   - Class-skill pop would cannibalize scoring-day speedup minutes (quantified: −X potential points).
   - Cooldown drifting toward a dead-day pop; hold Y hours to re-phase.
   - Recommendation based on estimated rates (flag).
   - Threshold reached — stop spending (per-day and per-tier).

### 3.4 Output shape
Dated recommendation stream in local time, e.g.:
- "Tue 9:00 AM — Pop **Instabuild** (~240k, verified-ish) then burn ~4h building speedups (2×1h, 1×3h short)."
- "Thu 8:00 PM — Start B2: [item], 2d 14h → lands Fri within power window; feeds Sat depth."
- "Ready now, **hold**: Instant Research until Sun evening (dead day; popping now forfeits ~75k Sat potential)."

## 4. Architecture (three legs)

### Leg 1 — Planner page (static, GitHub Pages)
- Single-page app in `palmon-tools`, client-side only. All timezone math via `Intl` + fixed UTC-2 epoch handling.
- State (queues, inventory, timestamps, weighting) in `localStorage`; import/export as JSON for durability.
- Reads shared `schedule.json` (FotP anchor, stages, Duel week, scoring config).
- Renders: now-strip (current FotP stage + Duel theme), double-dip calendar, recommendation stream, warnings, cooldown timelines.

### Leg 2 — Reminder pipeline (GitHub Actions cron → Discord webhook)
- **Load-bearing, not optional:** manual-fire abilities mean plan value only materializes if something pings at pop moments.
- Cron every 30 min at offset times (`7,37 * * * *`); all timezone/DST intelligence in the script (`zoneinfo`), never in cron expressions.
- Reads the same `schedule.json` + a small state file; computes reminders due since last successful run (Actions cache for state; cold-cache lookback capped at 45 min to prevent replay).
- Posts embeds to Adam's private planner channel using Discord `<t:unix:t>` timestamps. Webhook URL stored as repo secret. `workflow_dispatch` + `--dry-run` for safe testing.
- Reminder classes: pop moments (including end-of-hold), burn-window opens, queue-depth warnings, FotP re-anchor nag at event start.
- Guardrail: `expires` on the FotP anchor — past it, reminders flip to "⚠️ verify new event timing" instead of confidently announcing stale rotations.
- Adam builds channel + webhook; guidance provided for repo secret, YAML workflow, state file (small: one secret, one YAML, one JSON).

### Leg 3 — Fire-confirmation loop
- When an ability is popped, timestamp it (v1: a button on the planner page writing to localStorage; stretch: Discord reaction → Action updates state). Planner recomputes all downstream recommendations from confirmed reality. One missed confirmation ⇒ stale plan; the page surfaces "last confirmed fire" ages prominently.

## 5. Maintenance Budget & Update Rituals
- **Per FotP event (~30 sec):** one calendar screenshot → update anchor (start date + Day-1 stage).
- **Per new stage-rate screenshot (~30 sec):** overwrite that stage's scoring block; flag flips to verified.
- **Weekly (~1 min):** refresh queue contents + inventory ballpark; confirm fires as they happen.
- **Never:** building/research cost databases; per-patch data mining; server infrastructure.
- Hosting: GitHub Pages (free). Actions: free on public repo; comfortably within free tier if private.

1. **P0 — Model + page skeleton:** `schedule.json` schema, rotation/Duel projection, now-strip, double-dip calendar. (Immediately useful standalone.)
